# 多 Agent 智能客服系统 — 项目方案与复盘

> 本文档说明系统定位、架构设计、核心实现与开发过程中的问题复盘。配套 GitHub 仓库（README / 架构图 / 部署文档 / 界面截图）一起阅读。
> 项目状态：独立完成 0-1 开发，已在云服务器完成部署与端到端功能验证。

## 一、项目概述

**定位**：面向电商/智能硬件售后场景的多 Agent 协作客服系统——用户一句话进来，系统自动识别意图并转交最合适的专科 Agent 处理，回答质量不达标时自动转人工。

**要解决的痛点与对应方案**

| 痛点 | 解决方案 | 用户价值 |
| --- | --- | --- |
| 单一 Agent 承担全部职责：提示词臃肿、工具混杂，各类问题都难以答精 | 前台接待统一受理，按意图路由给 5 个专科 Agent，各配独立工具链 | 每类问题由最合适的 Agent 处理，回答更专业 |
| 结构化数据（订单号、产品名）用向量检索查询，准确率低 | 混合数据源：订单/产品走 SQL 精确查询，FAQ 走向量语义检索，外部信息走联网 | 查得准，不因"技术栈统一"牺牲精度 |
| AI 生成耗时数十秒，等待期间不确定系统是否理解 | 全链路 SSE 流式输出 + 消息气泡实时意图标签与置信度 | 等待过程可见、可感知 |
| AI 回答质量不佳时，用户没有出路 | 四维质量评估 + 低分自动触发转人工闸门 | 质量不达标时有兜底路径，问题最终能得到解决 |
| 提问超出 FAQ 覆盖范围 | 技术支持 Agent 按需加载专家排查 Skill；产品咨询未命中时建议联网搜索 | 非常见问题也能得到处理 |
| 刷新页面或更换设备后对话记录丢失 | 多轮状态持久化 + 会话管理，历史回看保留意图标签 | 对话可延续，历史可追溯 |
| AI 服务故障时页面报错、体验中断 | 网关降级：AI 服务不可达时返回友好提示，不返回 500 | 服务异常时平稳降级 |
| 担心会话被其他用户看到 | 会话归属校验（防水平越权） | 数据隔离，保障用户隐私 |

**核心能力**

- 7 节点 LangGraph 编排：前台接待（结构化输出，一次调用完成意图分类 + 闲聊回复）→ 条件路由 → 专科 Agent → 质量评估 → 转人工闸门
- 5 个专科 Agent 各配独立工具链，混合数据源（ChromaDB / SQLite / MCP 联网搜索）
- 四维质量评估（相关性 / 完整性 / 专业性 / 有用性），低分自动升级人工
- 双层流式：进度与意图事件 + LLM 逐 token，前端实时意图标签 + 打字机效果
- 全链路容错降级：咽喉节点降级转人工、MCP 两层防御、质量评估失败不阻断主流程
- 完整业务形态：JWT 登录认证、会话管理、意图标签落库可审计，前后端分离

**技术栈**

| 层 | 技术 |
| --- | --- |
| 前端 | Vue 3 / Vite / axios / markdown-it + DOMPurify |
| 业务后端 | Spring Boot 3.5 / MyBatis / MySQL / JWT（jjwt）+ BCrypt / RestClient |
| AI 引擎 | Python / FastAPI / LangGraph / LangChain（create_agent、create_deep_agent）/ ChromaDB / SQLite / MCP / Agent Skills / 通义千问 |
| 部署 | Docker 多阶段构建 / docker compose / 镜像仓库（ACR）/ 阿里云 ECS |

## 二、系统架构

```
浏览器（Vue 3 单页应用）
    │  JWT 鉴权（Authorization: Bearer <token>）
    ▼
Spring Boot 业务后端（:8082）—— 唯一对外网关
    ├─ 用户体系：注册 / 登录 / 角色
    ├─ 会话管理：会话归属校验 + 意图标签落库（可审计回看）
    ├─ AI 转发：SSE 流式透传（注入 X-User-Id 可信头）
    ▼
Python 多 Agent 引擎（:8001）—— 内部 AI 能力层，不对外暴露
    ├─ LangGraph 7 节点编排 + 5 个专科 Agent
    ├─ ChromaDB（FAQ 向量） / SQLite（订单、产品） / MCP（百度搜索）
    └─ SQLite checkpoint（多轮上下文）
```

**为什么分两层（Java 网关 + Python 引擎）**

| 考量 | 说明 |
| --- | --- |
| 职责分离 | Java 擅长业务系统（鉴权、事务、审计），Python 在 AI 生态最成熟，各用所长 |
| 安全边界 | 引擎不对外暴露端口，所有流量经网关；用户身份由网关注入，引擎不感知用户 |
| 可替换性 | AI 引擎可独立升级/替换（换模型、换 Agent 框架），业务侧接口契约不变 |
| 归属清晰 | 用户、会话、意图标签等业务记录在业务侧 MySQL（权威记录） |

## 三、Agent 编排设计（LangGraph 7 节点）

```
START → receptionist（前台接待）→ 条件路由
                                    ├── chitchat / escalate → respond → END
                                    ├── tech_support   ┐
                                    ├── order_service  ├→ quality_check → 闸门 → escalate_final / respond → END
                                    ├── product_consult┘
                                    └── web_search → respond → END（跳过质量检查）
```

**Coordinator 模式：前台接待一次调用做两件事**

Receptionist 用结构化输出（JSON Mode）在一次 LLM 调用里同时完成**意图分类**和**自然语言回复**：闲聊直接答复、投诉直接表达歉意并转人工，业务意图则输出引导语后路由给专科 Agent。

好处：
- 闲聊/转人工**不需要**走专科 Agent，省一次 LLM 调用；
- 用户总能立刻收到一句回应（"好的，帮您处理"），不会产生系统无响应的错觉；
- 分类与回复由同一次推理产出，意图与话术天然一致。

**条件路由**：根据意图在图上分叉——不是固定步骤，而是由状态决定下一步。这是 Agent 系统与固定管线（如 RAG 5 节点）的本质区别。

**双层流式：为什么不能统一用一种 stream_mode**

| 层 | 模式 | 原因 |
| --- | --- | --- |
| 外层编排图 | `custom` | 需要推送自定义业务事件（进度、意图、完成），完全自控格式 |
| 内层 Agent | `messages` | 内层是 `create_agent` 生成的图，拿不到 `writer()`，只能取 LLM 的原始 token |

一个 Graph 只能有一种 `stream_mode`。内层 token 通过 `handle_stream()` 逐 token 接住、再用 `writer()` 转入外层的 custom 通道——`handle_stream()` 的职责就是"把 messages 模式转成 custom 模式"。

**专科 Agent 与工具链**

| Agent | 数据源 | 工具 |
| --- | --- | --- |
| 前台接待 | — | 无工具（纯结构化输出分类 + 回复） |
| 技术支持 | ChromaDB | FAQ 向量检索；FAQ 未命中时按需加载 Agent Skill 排查流程 |
| 订单服务 | SQLite | 订单查询、物流跟踪 |
| 产品咨询 | SQLite | 产品搜索、预算推荐 |
| 联网搜索 | MCP | 百度搜索（外部 HTTP） |

每个 Agent 由 `create_agent` 创建——底层是 **ReAct 循环**：LLM 自主决定调不调工具、调哪个、调几次，工具结果追加回消息列表，LLM 判断够了就输出最终回复。与固定管线的区别是"路径由模型决定，而不是写死的节点顺序"。

## 四、质量保障与转人工

**四维评估**（满分 100）：相关性 / 完整性 / 专业性 / 有用性，各 25 分；换算为 0-1 分后低于 **0.6** 触发转人工。

**双重闸门**：

```python
if needs_escalation:        # 语义层：LLM 判断用户情绪激动 / 明确要求人工
    return "escalate_final"
if quality_score < 0.6:     # 质量层：回复不达标
    return "escalate_final"
return "respond"
```

两种触发互补——一个判断是否需要转接人工，一个判断回答质量是否达标。

**联网搜索跳过质量检查**：联网结果来自外部网页，本地 LLM 无法验证其真实性，强行打分反而误导。

## 五、工程化实践

**1. 意图标签随流落库，历史回看带徽章**

意图事件在回答**之前**到达，Java 网关在透传时旁路记录意图并随 AI 消息落库（不依赖最后一个 `done` 事件）——长流程被超时掐断也能留下标签，历史会话回看时每条回复都带意图徽章。

**2. SSE 原样透传**

Java 网关逐行原样转发引擎的 SSE 流，只劫持 `done` 事件附加 `session_id`；格式定义只在引擎侧一处，前端解析逻辑简单可靠。

**3. 容错降级按分支粒度设计**

多 Agent 是带路由的图，每个 Agent 是独立分支——单个 Agent 异常不影响其他分支：

| 组件 | 失败场景 | 降级行为 |
| --- | --- | --- |
| 前台接待（咽喉节点） | LLM 调用 / JSON 解析失败 | 降级为转人工（置信度 0.0），管线不中断 |
| 4 个专科 Agent | LLM 异常 | 返回降级提示，已产出的内容照常显示 |
| 质量评估 | 评估 LLM 异常 | 中性分 60 + 不转人工，不阻断主回复 |
| 联网搜索（MCP） | 启动时连不上 | 空工具列表启动，系统照常可用 |
| 联网搜索（MCP） | 运行中服务挂 | 已有内容照常输出，无内容给友好提示 |

**MCP 两层防御缺一不可**：初始化期故障（Agent 还没创建出来）由依赖层兜底；运行期故障（Agent 已创建）由 Agent 自身兜底——两者覆盖的时间点不同。

**4. Agent Skill 渐进式披露：FAQ 快速通道 + Skill 兜底**

技术支持 Agent 优先查 FAQ（快速、成本低）；FAQ 未命中时才加载 Skill（结构化排查流程）。Skill 启动时只暴露"名字 + 简介"，需要时 Agent 自行读取完整内容——避免把所有专家知识一次性塞进上下文。

## 七、项目复盘

> 以下为开发过程中真实遇到并解决的问题，以及关键设计决策的取舍分析。选取标准：体现设计权衡、边界处理或数据一致性，而非单纯的 API 使用细节。

**1. 两层流式：为什么不能用同一种模式**

- **问题**：内层 Agent 的 token 无法直接推给前端，外层还要推意图/进度事件。
- **定位**：`create_agent` 生成的内层图不暴露 `writer()`，用不了 custom 模式；外层若改用 messages 模式，意图分类的裸 JSON 会混进前端；一个 Graph 只能有一种 stream_mode。
- **解决**：内层 `messages` 取 token → `handle_stream()` 逐 token 接住 → `writer()` 转入外层 custom 通道 → 外层 `custom` 统一推送结构化事件。
- **沉淀**：**嵌套结构中，跨层数据需要显式转换**——把内层的输出协议转换为外层的输出协议，而不是依赖框架自动打通。

**2. 前台接待的选型：分类与回复合并为一次调用**

- **背景**：最初的设计是"独立的意图分类器 + 单独的分类节点"，后来改为 ReceptionistAgent 一次结构化输出同时完成分类与回复。
- **权衡**：分离式的好处是职责单一，但代价是闲聊/转人工也要多走一次 LLM；合并后省一次调用，且**分类结果与用户看到的回话由同一次推理产出**，不会出现"分类说转人工、话术却在挽留"的割裂。
- **沉淀**：**能用一次调用解决的两件事，不要拆成两次**——尤其是当两件事共享同一份推理上下文时。

**3. 混合数据源：什么数据该用什么查**

- **选型**：订单号/产品名是**精确匹配**，用 SQLite 结构化查询（`WHERE id = ?`）；FAQ 是**语义匹配**（"蓝牙连不上" vs "连不上蓝牙"），用向量检索；商品参数/行情等**外部实时信息**走 MCP 联网搜索。
- **反面**：如果全部塞进向量库，查订单号会因"ORD001 与 ORD002 向量接近"而返回错误订单——结构化数据的精度优势被抹掉。
- **沉淀**：**数据源按查询语义选**，不是按"技术栈统一"选。

**4. FAQ 的数据结构：问题做向量，答案放 metadata**

- **设计**：FAQ 的 `page_content` 存**问题**（用于相似度匹配），`metadata.answer` 存**标准答案**。检索命中后直接返回答案，不需要 LLM 再从文档内容里提取。
- **对比**：RAG 是把文档内容切块做向量——适合"从长文本中找依据"；FAQ 是"问-答"对，**答案本身不需要被检索**，只需要被找到。
- **沉淀**：**数据结构要匹配使用方式**——同样的向量库，存什么、查什么，取决于业务是"找依据"还是"找答案"。

**5. 质量检查的边界：校验者的能力决定它能否校验**

- **问题**：联网搜索返回了准确结果，却被质量检查判为"编造内容"，触发转人工。
- **定位**：质量检查用的 LLM 没有联网能力，无法验证网络搜索结果，自然认为数据是虚构的。
- **解决**：`web_search → respond`，跳过质量检查节点。
- **沉淀**：**一个校验环节只能校验它有能力验证的东西**；让无能力者参与判断，只会引入误判。

**6. 有持久化状态时，一次性字段必须每轮重置**

- **问题**：上一轮触发了转人工，新一轮走正常路径，前端仍弹出转人工横幅。
- **定位**：checkpoint 保存了全部状态，上一轮写入的 `needs_escalation=True` 在第二轮没有被任何节点覆盖。
- **解决**：每个节点显式返回该字段的当前值（含 `False`），保证每轮重置。
- **沉淀**：**持久化状态里没有"默认值"这个概念**——不显式覆盖就等于沿用上一轮。

**7. Agent 场景的 LLM 重试：包装方式要与消费方匹配**

- **问题**：给 LLM 工厂统一加 `with_retry()` 后，4 个 Agent 全部崩溃。
- **定位**：`with_retry()` 把模型包成 `RunnableRetry`，只转发 invoke 类方法，不转发 Agent 框架需要的 `bind_tools` 与模型名解析。
- **解决**：Agent 场景改用官方 `ModelRetryMiddleware`（作为 middleware 传入，在框架内部包装模型调用）；纯 `invoke` 场景（意图分类、质量评估）保留 `with_retry()`。
- **沉淀**：**"只有 A 有问题"往往是表面结论**——最初只发现 deep_agent 报错，测到第二个 Agent 才暴露 create_agent 同样不兼容；排查兼容性问题需要对同类调用方逐一验证。

**8. 数据与索引的一致性：换 Embedding 模型必须重建向量库**

- **问题**：FAQ 数据明明存在，检索却始终为空。
- **定位**：`data/chroma_db/` 目录被清空后未重建（ChromaDB 持久化 = 元数据 + HNSW 索引目录，缺一不可）；且更换 Embedding 模型后向量空间不兼容。
- **解决**：删除空目录后由种子逻辑自动重建；固化"换模型 = 重建索引"的操作纪律。
- **沉淀**：**向量库是"数据 + 模型"的绑定产物**，换模型不能只换配置。

## 九、当前局限与演进方向

**当前定位**：单机演示部署（单实例），已完成端到端验证，未做压力测试；容量适合小规模试用与演示。

**已知瓶颈**

| 环节 | 现状 | 影响 |
| --- | --- | --- |
| Python 引擎 | 单进程单事件循环（uvicorn 单 worker） | 单次请求需经过接待员分类 + 专科 Agent 多轮 ReAct + 质量评估，LLM 调用次数多；并发数上升后排队 |
| 会话状态 | SQLite checkpoint（单文件、写事务串行） | 小并发无感；**水平扩展的硬约束**——文件级数据库无法多实例共享 |
| 质量评估 | 同步串在链路中，每次回复额外消耗一次 LLM 调用 | 增加单请求延迟与 API 成本；并发下放大配额压力 |
| 外部依赖 | 大模型 API、MCP 联网搜索服务 | 账号级 QPS 限制；MCP 为第三方服务，可用性不可控（已有两层降级） |
| 业务库 | MySQL 单实例，连接池默认上限 | 并发数据库操作超过池上限时排队 |
| 机器资源 | 2 核 4G 单机 | CPU 与内存上限 |

**演进路径**（按优先级）

1. **先观测再扩容**：接入监控（请求延迟、错误率、并发数、各 Agent 调用分布），有数据再决定扩容方向；
2. **限流与排队**：网关层令牌桶限流 + 超载排队，让请求等待而非打挂服务；按意图分流，闲聊/FAQ 快路径优先；
3. **降低单请求成本**：意图分类与质量评估属于判断类任务（分类、打分），可换用轻量模型，或先规则粗筛、可疑的才调主模型复核——主模型留给回复生成；
4. **引擎多实例**：uvicorn 多 worker / 多容器 + Nginx 负载均衡；
5. **状态外移**：SQLite checkpoint → Postgres（LangGraph 官方 PostgresSaver），使多实例可共享会话状态；
6. **外部依赖加固**：MCP 结果缓存、多搜索服务源切换；
7. **成本控制**：LLM 响应缓存、按用户配额。
